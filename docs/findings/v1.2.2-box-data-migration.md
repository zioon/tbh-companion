# v1.2.2 BoxData 数据结构迁移记录

> 类别：研究成果（findings）。结论形成时间：2026-09-09。
> 相关业务流程：`docs/BUSINESS-FLOWS.md` 之 **13. ChestService**、**14. AutoClassify**、**6.1 parseInventory**。

## 背景

用户报告：v1.2.2 更新后「物品自动归类失效，slots 数量都成 0」。诊断确认该问题根因是 **v1.2.2 大版本对「宝箱持有数据」的存档与运行时结构做了整体迁移**，并非普通回调/偏移漂移。

自动归类（AutoClassify）依赖 ChestService 提供的 per-category 宝箱槽位数量（`slots: {common, rare, act}`）来校准 FIFO 队列。该数量原本来自两个数据源，v1.2.2 下两条全部无法提供，导致 reconcile 每次用 `slots=0` 把新掉落的入队项剪掉（日志：`reconcile: pruned N excess <cat> item(s) (queue N > slots 0)`），归类彻底失效。

## 证据

### A. 存档层（可复现地解开 `SaveFile_Live.es3`）

- 整个明文存档（`PlayerSaveData`）中 **不存在** `BoxData` / `BoxTypes` / `BoxQuantity`（命中数均为 0）。
- v1.2.2 改用两个新字段代替：
  - `BoxBucketUseBoxList`: `string[]`，元素形如 `"551278195918943844"`
  - `BoxBucketGetBoxList`: `string[]`，元素形如 `"551278195918943853"`
- 这些 id 是 **ES3 全局自增实体引用号**，非类型/数量编码：
  - 全部共享前缀 `551278195918943…`，仅末尾 +2 递增；连续观测几分钟内 `UseBoxList` 从 6 条增长到 38 条，`GetBoxList` 稳定在 2 条。
  - 数值区间内存在空洞（被物品/符文等其他实体的递增号占用），进一步证明是全局递增 id，不含箱型信息。
- 其余保存数据结构完好：`itemSaveDatas`、`inventorySaveDatas`、`commonSaveData`、`RuneSaveData`、`PetSaveData`、`currenySaveDatas` 等均正常。
- 全局顶层 key 只有 `AccountSaveData` / `PlayerSaveData` / `SystemInfo`，无独立 BoxBucket 实体定义。

**结论**：v1.2.2 存档层**不再包含「每类箱子（普通/稀有/精王）的持有数量」**。老式 `parseChests`（读 `BoxData.BoxTypes/BoxQuantity`）必然解析出 0 个箱子。

> **⚠️ 更正（2026-09-10）**：此结论错误。未开箱子以普通物品形式存在于 `itemSaveDatas`（STAGEBOX 物品），`UniqueId` 与 `BoxBucketGetBoxList` 一一对应——当时只检索了 `BoxData`/`BoxTypes` 等 key 名，没有把 bucket id 放到全文中追踪落点。见文末「最终落地更正」。

### B. 运行时层（对运行中的 v1.2.2 进程做 IL2CPP 扫描）

工具：复用项目 `winProcess.ts` + `core/liveMemory/il2cppScanner.ts`，esbuild 打包为独立 node 脚本 attach 读内存（`GameAssembly.dll` base `0x7ff945720000`，size `0x6b2b000`）。

- `collectClassEntries` 建立 10897 个命名类索引成功。
- `findPlayerSaveData(...)` → **null**：`CommonSaveData` 单例静态字段在 v1.2.2 **不可读**（与 v1.01.05 同，属既有「预期降级」路径；过去靠存档兜底，现存档也没箱子数据）。
- `findBoxDataStructurally(...)` → **null**（GA 范围内找不到 CommonSaveData/PlayerSaveData 持有者实例）。
- `CommonSaveData` 类字段表自 `0x010` 至 `0x079`，**没有 `BoxData` / `bucket` 字段**。
- v1.2.2 新增/保留的箱子相关类：
  - `EBoxType` 枚举：`NORMAL` / `BOSS` / `ACTBOSS`（即 common / rare / act 三类，语义保留）
  - `bucket[]`、`StageBox[]`（数组类，元素类 `bucket` / `StageBox`）
  - `HeaderBucket`、`box`
  - `BoxCreateItem` `{ o_itemId, o_count, o_dropKey; itemId, count, dropKey }`、`BoxCreateItem[]`
  - `BoxOpenLog`（字段被混淆为 `bgug/bguh/bgui`）、`GetBoxLog`（`bgvm/bgvn/bgvo`）
  - `InventoryProcessBoxResult`

**结论**：v1.2.2 运行时把宝箱改成了「bucket / StageBox 桶」体系，且其持有对象不挂在 CommonSaveData 可达路径上。每类箱子数量在运行时需另找可达单例。

### B2. 运行时 `BoxData` 类 **重构**（关键！）

继续对同一进程做值扫描（用存档里的 bucket id 字符串 `551278195918943…` 在进程内存中定位），反向定位到它们的持有对象，确认 v1.2.2 运行时**仍存在 `BoxData` 类，但改成「每个箱子一个实例」**：

```
class BoxData (v1.2.2)
  o_itemId@0x10        // obscured 原始
  o_itemKey@0x20|0x28|0x30|0x40|0x48 ...   // obscured 字段组
  itemId@0x54   int    // 观测值 = 910901 —— 箱型/物品码，用于分 common/rare/act
  itemKey@0x58  string // = bucket id，如 "551278195918943867"
  claimableAt@0x60 string // ISO-8601 UTC，如 "2026-09-09T10:02:43Z" —— 自动开箱可领取时间点
  rewardItemId@0x68 int=0   // 开箱奖励（未开前为 0）
  rewardItemKey@0x70 int=0
  isGet@0x78     int=1      // 是否已领取
```

观测语义（用户确认玩法未变）：
- **每个活着的箱子 = 一个 `BoxData` 对象**，携带 `claimableAt`（自动开启时间）与 `itemId`（箱型）。
- 这正是 AutoClassify「serial-queue + autoOpenAt」模型的运行时来源：旧按类记大数，v1.2.2 改为逐对象（每箱一个可开时间）。
- 活跃实例数与存档 `BoxBucketGetBoxList` 长度吻合（观测 2 条）。`BoxBucketUseBoxList`（38+，持续增长）为已用/归档引用。
- 持有这些 BoxData 对象的**容器入口与 `itemId→EBoxType` 映射仍未最终确认**（对象被多个字段引用，非标准 List）。

修复需要：定位持有全部存活 BoxData 的容器/根对象，按 `itemId` 分组计数喂给 `readRuntimeChestSlots`，并把 `claimableAt` 映射进 AutoClassify 队列。

### B3. 精确容器入口的尝试结果（2026-09-09 第二轮）

对运行进程做了「字符串→对象→父容器」的多轮逆向：

- 用「对象头 == `BoxData` classPtr + 结构校验（`itemId` 合理 + `itemKey` 是 .NET string）」从全内存命中中过滤，**当前仅得到极少数真实活跃实例**（观测为 1–2 个），`claimableAt` 常见为 `null`（下 `isGet` 语义待确认）。
- 活跃实例数与存档 `BoxBucketGetBoxList` 长度口径一致；`BoxBucketUseBoxList`（持续增长）为历史/已用引用。
- **关键卡点**：这些 BoxData 对象由多个不同字段引用（非单一 List），且地址随托管堆 GC 移动；`CommonSaveData` 单例静态字段在 v1.2.2 不可达，**尚未找到可稳定重复定位的根/容器入口**。

**影响**：新 `BoxData` 的「逐箱对象 + 每箱一个 `claimableAt`」结构本身可直接映射 AutoClassify 的 serial-queue + autoOpenAt 模型；但要使 `readRuntimeChestSlots`（25Hz）能稳定读到每类数量，必须先把根容器对象（某可达 Manager / PlayerSaveData 归属）确定下来。此项是完整落地的主要剩余不确定点。

### B4. PlayerSaveData 已定位（2026-09-09 第三轮）

- 通过字段签名（`BoxBucketUseBoxList`/`GetBoxList` + `itemSaveDatas`/`RuneSaveData`/`PetSaveData`/…）定位到 v1.2.2 的 **`PlayerSaveData` 混淆类名 = `ti`**，并在运行时找到其实例，完整 dump 字段。
- **重要结论**：`ti`(PlayerSaveData) 只含 `BoxBucketUseBoxList@0x18` / `BoxBucketGetBoxList@0x20` 两个 **id 引用列表**，并**不含**「每类箱子数量」，也**不含** BoxData 集合。与存档结构一致。
- 因此存量箱子（每类数量 + `claimableAt`）由**另一个独立的对象/Manager（BoxBucket/BoxData 管理器）持有**；该对象字段名被混淆、非静态直达、地址随 GC 移动，尚未被稳定定位。
- 每次对它的定位尝试都要做一次全内存扫描（数秒级），且结果随游戏运行/GC 漂移——这正是「完整落地」的主要剩余工作量，也是建议用「游戏内箱子界面截图」的数值对齐来加速收敛的原因。

### B5. 引擎可运行 + 收敛到「逐箱 BoxData」存活实例（2026-09-09 第四轮）

用可靠引擎（值扫描取 `Bucket-id 字符串 → 唯一引用槽 → ref-0x58 = BoxData 对象 + 结构校验`）批量枚举：

- **引擎稳定可运行**：能 attach 运行中的 v1.2.2 进程，单次全内存扫描约 6s，可靠识别出真正存活的 `BoxData` 实例（对象头指向 BoxData 类，`itemId` 在合理范围，`itemKey` 是 .NET 字符串）。
- **收敛实测**：经两次独立扫描，v1.2.2 当前**仅 1 个存活 BoxData 实例**（`itemId=69`、`itemKey=551278195918943996`、`claimableAt=null`）。结合用户提供的游戏截图（普通宝箱显示「0/时」、两个箱子在自动开启计时），**运行时每类箱子数量与界面显示完全吻合**。
- **含义**：v1.2.2 新 `BoxData` 是「每个箱子一个对象」，其**总存活数 = 每类箱子持有数**（按 `itemId` 分组即 common/rare/act）。`claimableAt`（自动开启时间）直接对应 AutoClassify 队列的 `autoOpenAtMs`。用户确认玩法未变 → 模型无需改动，只要把数据源接到「按 itemId 分组的存活 BoxData 计数」即可。
- **剩余工作**：① 定位持有全部存活 BoxData 的**根容器/List<BoxData>**，使 25Hz 读取可稳定遍历（非每次全内存扫描）；② 确认 `itemId → EBoxType`（NORMAL/BOSS/ACTBOSS → common/rare/act）映射。

### B6. 容器逐级回溯：确认 BoxData 属 GC 可移动（2026-09-09 第五轮）

从已验证的存活 `BoxData` 出发逐级回溯父容器：

1. **找到 `List<BoxData>` 容器**：`0x253da6f2180`，`size=2`，backing `BoxData[]`（容量 4）。两条目各项与界面实况吻合（两个普通宝箱，`itemId=910901`，`claimableAt` 分别为 `2026-09-09T11:31:53Z`、`12:29:15Z`，`isGet=1`）。
2. **该 List 唯一引用** `0x253da858ea0` 是某数组 `0x253da858e10` 的 `[14]`（len=72），但**该数组无人引用**（全内存扫不到指向它的 `_items`）。
3. **结论**：这个 `List<BoxData>` 处于 GC 整理中的**游离/易失**状态——它不挂任何稳定静态根，地址随托管堆移动。这正是「内存里每类箱子数量无稳定入口」的根因：v1.2.2 的箱子状态对象是**运行时生命周期对象（可被 GC 移动）**，不带静态引线。
4. 反复核实游戏面箱子类名全集仅 `BoxCreateItem` / `EBoxType` / `BoxOpenLog` / `GetBoxLog`（`BoxData`、`BoxBucketUseBoxList`/`BoxBucketGetBoxList` 均属于 `ti`=PlayerSaveData）；不存在「BoxBucket 管理器」业务类名。`box/bow/bov/bou/bot`（`bjdw/bjdv/...`@0x0 指向自身）是 Unity 引擎内部 NativeClass 封装，已排除。

**技术判定**：v1.2.2 的「每类箱子数量」只能通过 **迭代所有存活 `BoxData` 对象并按其 `itemId` 分组** 得到；这些对象只能靠「从 Bucket-id 字符串回溯」或「对象头扫描 + 结构校验」发现，均为全内存级操作。这与旧版「`CommonSaveData` 静态 → `BoxData` 固定偏移 → 两列 `List<int>`」的 O(1) 结构**不同**：

- 旧：静态直达 + 固定列表 → 可 25Hz 廉价读取。
- v1.2.2：GC 对象集合 → 需持续枚举（全内存级）。

**落地含义**：AutoClassify 的模型（per-category 串行队列 + `autoOpenAtMs` = `claimableAt`）**无需改动且成立**；但 `readRuntimeChestSlots` 无法用静态偏移廉价实现。可行方案：
- **方案 A（0 基）**：以存档 `BoxBucketGetBoxList`/`UseBoxList` 的差集为准（存档每次落盘即稳定点），配合 `claimableAt` 语义恢复每类数量 —— 满足「自动归类基本可用」，非实时。
- **方案 B（实时，重）**：将逐箱 `BoxData` 的「对象头+结构校验」枚举做成低频率（秒级）后台任务，喂给 AutoClassify（降低实时性要求，与 AutoClassify 本身秒级 reconcile 匹配）。
- **方案 C**：放弃 live 路径，退回 save 解析（需先解决 v1.2.2 存档无逐类数量的问题）。

## 根因链（AutoClassify slots=0）

```
save 层: parseChests 读 BoxData(无) → chests=[] → slots={0,0,0}
live 层: CommonSaveData 单例不可达 → boxData offset 未派生 → readRuntimeChestSlots=null
        → ChestService 仅有 save 快照（全 0）
reconcile(slots=0): AutoClassify 把入队的真实掉落当"已开"prune → 队列无法维持 → 自动归类失效
```

## 修复方向（v1.2.2 适配专项）

要让自动归类恢复「每类箱子数量」，需在以下二者择一建设数据源，二选一或并行：

1. **运行时新结构逆向**（优先）：找到持有 `bucket` / `StageBox` / 每类计数的**可达单例**（不在 CommonSaveData 上），为 `readRuntimeChestSlots` 派生新偏移；同时核对 `BoxOpenLog`/`GetBoxLog` 混淆字段（`bgug…`），必要时为 loot/unclassified 追踪补适配。
2. **存档语义还原**：理解 `BoxBucketGetBoxList` / `BoxBucketUseBoxList` 如何映射到每类数量与 auto-open 状态（需游戏内 DB / 公告对照，或多时刻存档比对做语义回归）。

任何落地改动都需同步更新：
- `app/src/core/inventory/parse.ts`（`parseChests`/`ChestHolding` 数据流）
- `app/src/main/services/ChestService.ts` + `app/src/core/boxes/*`
- live memory: `il2cppScanner` / `offsets.ts`（新增 v1.2.2 bundle 表）
- `docs/BUSINESS-FLOWS.md`（第 13/14/6 章）、`docs/SAVE_FORMAT.md`

## 落地结果（方案 B，2026-09-09 已编码 + 单测）

选定的落地路线为**方案 B（运行时逐箱 BoxData 枚举兜底）**，AutoClassify 的 per-category 串行队列模型不变：

- **core**（`app/src/core/liveMemory/chestSlots.ts`）：新增
  - `readLiveBoxDataSlots(reader, instances, offsets, itemIdToCategory)` — 对存活 BoxData 实例按 itemId 分组计数为 `{common,rare,act}`。
  - `readBoxDataItemId` — 实例指针校验 + 读 itemId（`+0x54`）。
  - `categoryFromBoxItemName` / `buildV122ItemIdToCategory` — 按 gamedata 物品名前缀（Normal/Stage Boss/Act Boss）分类。
- **main**（`liveReader.ts` / `worker.ts` / `liveMemoryService.ts` / `appState.ts`）：
  - liveReader 新增 `readV122LiveBoxSlots`（GA 类索引找 BoxData classPtr → 清堆扫头 + 结构校验 → 计数），经 `V122_SCAN_CACHE_MS`=3s 节流，仅在旧静态读取 null 时兜底。
  - appState 在 loadGameData 后把 `itemId→category` 映射经 liveMemoryService → worker 注入 reader。
- **测试**：`test/core/liveMemoryChestSlots.test.ts` 新增 8 用例（读取聚合/分类/非法实例/空列表/指针校验/名称分类/映射构建），共 24 用例全绿。

**已知边界（须真机确认）**：清堆枚举单次秒级；虽有 3s 节流，但每次失效后仍需一次秒级扫描。已在 `pnpm dev` 下的真机（v1.2.2）验证前，无法确认扫描期的绝对开销。此项写入 `docs/BUSINESS-FLOWS.md` §13.5。

## 最终落地更正（2026-09-10）：方案 B 废弃，改 save 侧解析

方案 B 上线后从未生效，真机排查（日志逐跳追踪）发现两个叠加问题：

1. **方案 B 的投递链路断裂**：utilityProcess 子进程 `parentPort.on("message")` 回调收到的是事件对象 `{data: payload}`，worker 未解包 `data`，主进程下发的 `itemId→category` 映射静默丢失（`msg.type` 永远 undefined）。同一缺陷同时使 `stop` 指令失效，并潜伏在 `inventoryWorkerEntry.ts`（P1-6 库存 worker 的 init/ready 握手从未成功，一直静默回退主线程同步 resolve）。两处均已修复（统一在 handler 顶部解包）。
2. **更关键：方案 B 的前提是错的**。本文 §证据 A 判定「存档不再包含每类箱子数量」——当时只 grep 了 `BoxData`/`BoxTypes` 等 key 名。2026-09-10 把 `BoxBucketGetBoxList` 的 bucket id 放到存档**全文**中追踪落点，发现每个未开箱子的 id 都对应 `itemSaveDatas` 里一条 `{"ItemKey":910901,"UniqueId":<bucket id>,...}` 记录：`ItemKey` 即 gamedata 的 STAGEBOX 物品 id（`910901` Normal Monster Box / `920901` Stage Boss Box / `930901` Act Boss Box），名称前缀直接给出 common/rare/act 分类。实机验证：存档 4×910901 + 4×920901 与游戏内持有完全一致。

**最终方案（已上线）**：`parseChests`（`core/inventory/parse.ts`）在 `BoxData` 缺失时走 `BoxBucketGetBoxList` 路径——提取 id 字符串集合，在 `itemSaveDatas` 原始文本中按字符串匹配 `UniqueId`（超 `MAX_SAFE_INTEGER`，禁止转 number），`ItemKey` 作为 `ChestHolding.type` 并由 `InventoryService` 注入的 `classifyBoxItemKey` 产出 `category/label`；`resolveChestHoldings` 优先采用。方案 B 的内存枚举代码全部移除。真机验证：`reconcile: backfilled 5 common / 4 rare`，AutoClassify 恢复正常。

**经验**：
- 「某 key 不存在」≠「数据不存在」——实体引用号必须在全文中追踪其所有出现位置再下结论。
- worker 通信链路每一跳都要有日志证据；缺日志 = 链路断裂，不是「功能未启用」。
- 内存枚举（全堆扫描、GC 可移动对象、无稳定类名）应是最后手段；save 5s 轮询对槽位计数已足够。

# v1.2.2 英雄实时经验数据回退的根因与修复

> 类别：研究成果（findings）。结论形成时间：2026-09-10。
> 相关业务流程：`docs/BUSINESS-FLOWS.md` 之 **5. LiveMemory**（`readParty` 读取英雄队伍）、**5.5.2 英雄 live 读取稳健化**、**12.3 StageRun 失败检测**。

## 背景

用户报告：v1.2.2 更新后「英雄（实时经验）」持续显示**回退/错误**——要么整个英雄 tab 数据回退，要么显示数量不对、等级全错（曾出现"1 个 name=4 一级，实际 3 个 101 级"）。这是继 v1.2.2 BoxData 迁移之后，另一个大版本引起的 live-memory 解析回归。

## 排查过程（关键转折）

整个排查经过了多轮「看似对、实则在猜」的阶段，值得复盘以避免重蹈：

1. **最初误判为 `heroList` 偏移失效**。报错 `StageManager static block scan: 17 candidate(s) but none passed isLiveStageManager ... first fail=HeroList ptr null` 曾一度指向 `runtime.heroList` 偏移。据此加过 `probeHeroListOffset` 运行期改写偏移——**这是错误方向**。
2. **加诊断探针**：`heroes-parse dump` / `herocache-probe`（BFS 找 heroKey）/ `heroRuntime-dump` / `probe-meta`。这些探针最终揭示了真相，但早期 BFS 探针把问题引向「某些堆对象含合法 heroKey」的假象，模糊了根因。
3. **决定性证据**（`probe-meta`）：
   ```
   probe-meta gameVersion=1.2.2 fallback=none unit.cache=0x3b0 heroRuntime.info=0x30 heroInfoData.heroKey=0x30
   probe-rt heroPtr+uc(0x3b0)=0x… u32[…593,0,0,…]   ← rt 内无任何合法 heroKey(101/201/301)
   ```
   同时 `herocache-probe` 全队投票稳定命中 `uc=0x3d0 → info@0x30 = 301/201/401`。
4. **矛盾收敛**：运行时实际使用的 `unit.cache=0x3b0`，而正确值是 **0x3d0**（bundled / 磁盘缓存都是 0x3d0）。`readParty` 用错的 0x3b0 解出错误的 `HeroRuntime` → heroKey/level/exp 全部错位 → 英雄实时数据回退/错误。

## 根因

**运行时使用的 `LiveOffsets.unit.cache` 被定型为 0x3b0，而 v1.2.2 的正确值为 0x3d0。**

- v1.2.2 是布局迁移版本：`unit.cache` 相对 v1.01.05 由 0x3b0 → 0x3d0（+0x20），bundled 表与 extractor 输出均应为此值。
- 但 `mergeOffsets` / extractor 派生路径可能以更早的 base（如磁盘缓存里旧的 0x3b0 或 fallback base）合并出 0x3b0，运行时即稳定采用错误值。
- 一条错误偏移让整条 `Hero[] → heroPtr + unit.cache → HeroRuntime → heroInfoData.heroKey` 链全部解错，UI 表现为「英雄实时经验回退/数值全错」。

> 注意：`unit.cache` 不在 `mergeOffsets` 显式字段内，`mergeOffsets` 返回 `{...base, ...}`，`unit` 整体继承自 base；因此错误 base 的 0x3b0 会原样保留到 merged 结果并写回磁盘缓存。

## 修复

在 `LiveMemoryReader.applyResolvedOffsets` 增加与既有 `runtime.stage.alive` backfill 相同的逻辑：**用 bundled 表的 `unit.cache` 兜底**，当解析结果与 bundled 不一致时以 bundled 为准：

```ts
if (this.offsets && this.gameVersion) {
  const bundled = offsetsForVersion(this.gameVersion);
  if (bundled && bundled.unit.cache > 0 && this.offsets.unit.cache !== bundled.unit.cache) {
    this.offsets = { ...this.offsets, unit: { ...this.offsets.unit, cache: bundled.unit.cache } };
  }
}
```

这样即使磁盘缓存/extractor/merge 反应出 3b0，运行时应用到读取路径的偏移也会被强制校准为当前版本的 bundled 正确值 3d0。

## 启示（经验）

1. **大版本 live-memory 回归的第一怀疑对象不是「新增探测偏移」，而是「实际运行时该偏移的值与 bundled 表是否一致」。** 先 `probe-meta` 打印运行时 `o.unit.cache / heroRuntime.info / heroInfoData.heroKey` 实际值，比对 bundled——一条日志就能定位，比 BFS 扫描对象高效得多。
2. **BFS 找 heroKey 帮助定位「哪个偏移是对的」，但绝不能用作生产读取**；它会把「正确 heroKey 藏在某可达对象里」误当「现有偏移有效」。
3. **`unit.cache` 这类结构常量不应在 merge 时被错误 base 悄悄改掉**——`mergeOffsets` 对结构字段应优先取 bundled 权威值。至少在应用端补齐 backfill 兜底（本修复），防止错误缓存覆盖正确值。
4. 诊断探针用后即删，避免给 25Hz 读取路径留下永久额外内存读/log 开销。

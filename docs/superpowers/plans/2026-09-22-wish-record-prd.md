## 0. 原始需求复述

> 增加祈愿记录功能，能够自动记录祈愿的结果，并进行统计（参考掉落）。

用户希望在应用内新增「祈愿记录」能力：自动记录每一次祈愿的结果，并提供类似「掉落（Loot）」页那样的统计视图（累计 / 会话增量 / 速率 / 品质分布 / 单品排行 / 历史列表）。

**已确认的三项产品决策（本 PRD 强制体现）：**

1. **统计口径**：**「祈愿次数」与「产出物品总数」并列展示**。一次祈愿可能产出多件物品（游戏自带计数器统计的是物品数），因此必须同时给出两个维度的数字，各自的 per-hour 速率也都要给。
2. **展示位置**：**独立新 tab「祈愿」**，与 Loot、RecordLog 平级。
3. **统计范围**：**会话级（session）与累计（cumulative）并存**，沿用掉落的语义 —— 重置会话只清 session 增量，长期累计与归档文件不受重置影响。

---

## 1. 产品目标

**一句话目标**：让玩家能够自动、无感地记录「祈愿」的全部产出，并以与「掉落」一致的统计视角复盘祈愿收益与产出结构。

**三条可衡量的目标：**

| # | 目标 | 可衡量标准 |
|---|------|-----------|
| G1 | **零操作自动记录** | 玩家在游戏内完成祈愿后，应用无需任何手动操作即可在 ≤ 1 个推送周期（约 5 Hz 推送）内把本次祈愿结果计入统计；连续祈愿 N 次后统计条数应等于 N（不重不漏）。 |
| G2 | **两个维度可核对** | 面板同时给出「祈愿次数」与「产出物品总数」；玩家可与游戏内「祈愿获得的物品数」（`Satistics_TotalOfferingCount`）自行核对，物品总数误差应为 0（同一数据源、同一口径）。 |
| G3 | **与掉落统计体验一致** | 祈愿 tab 的信息结构（累计 / 会话 / per-hour / 品质分布 / 单品榜 / 历史列表）与 Loot tab 对应模块一一对齐，玩家零学习成本迁移；新增 UI 文案在 4 个语言（zh-CN / en / ja / ko）全部落地。 |

## 2. 用户故事

1. **As a** 长期肝游戏的玩家，**I want** 应用自动记录我每一次祈愿的结果，**So that** 我不必再手动截图或记忆到底出了哪些物品。
2. **As a** 关注收益效率的玩家，**I want** 看到本会话与历史累计的「祈愿次数 / 产出物品数」以及各自的 per-hour 速率，**So that** 我能判断当前祈愿节奏是否划算、值不值得继续投纪念币。
3. **As a** 追求高品质产出的玩家，**I want** 看到祈愿产出的品质分布（COMMON → CELESTIAL）与单品产出排行，**So that** 我能知道祈愿池里实际出了什么、稀有品质占比多少。
4. **As a** 复盘型玩家，**I want** 查看近期的祈愿历史列表（时间 / 物品名 / 品质色 / 数量），**So that** 我能回溯某次「欧皇/非酋」时刻。
5. **As a** 中途换角色或重开一段farm的玩家，**I want** 重置会话时只清空本次会话增量和速率、保留长期累计归档，**So that** 我既能干净地开始新一轮统计，又不会丢掉历史积累。

## 3. 需求池（P0 / P1 / P2）

> 优先级定义：**P0 = Must have**（最小可用集，缺一不可）；**P1 = Should have**；**P2 = Nice to have / could have**。

### P0 —— 自动记录 + 核心统计（最小可用集）

- **P0-1 自动捕获祈愿结果行（必须）**：从**现有稳定数据源**（游戏进程内存「获得记录」定长列表，经 `readRuntimeAcquireLogs` → `TrackingService.ingestAcquireBatch` 管道）中识别 `LogMessage_OfferingResult`（`祈愿结果：获得 {0}` / `Offering result: Obtained {0}`）类型的行，并结构化解析出 **名称 / 品质色 / 数量**（复用 `acquireLog.ts` 的解析能力）。**不得新增任何内存读取路径**。
- **P0-2 专属领域聚合（必须）**：在 core 层新增祈愿专属聚合器（对标 `ChestDropTracker`），维护：累计祈愿次数、累计产出物品数、品质分布、单品 breakdown、历史列表、会话基线。
- **P0-3 会话级 + 累计并存（必须）**：同时维护两套数字 —— **累计**（长期，不随会话重置清空）与 **会话增量**（重置会话后归零）。重置逻辑仅清 session，不动累计。
- **P0-4 双 per-hour 速率（必须）**：分别给出「祈愿次数 per-hour」与「产出物品数 per-hour」两条速率，费率分母口径统一（见 §5）。
- **P0-5 品质分布（必须）**：按 `COLOR_TO_GRADE`（COMMON / UNCOMMON / RARE / LEGENDARY / IMMORTAL / ARCANA / CELESTIAL，及无法判定时的「未知」）统计各品质的产出物品数与占比。
- **P0-6 单品产出排行（必须）**：按物品名聚合产出数量，降序排列，展示每个单品数量与占比。
- **P0-7 历史列表（必须）**：按时间倒序展示最近的祈愿产出记录（时间 / 名称 / 品质色 / 数量），条数上限与掉落历史保持一致口径。
- **P0-8 独立「祈愿」tab（必须）**：新增与 Loot / RecordLog 平级的 tab，承载上述统计面板。
- **P0-9 会话级持久化（必须）**：祈愿统计的 session 状态随会话重置 / 应用重启正确恢复与清零（对标掉落持久化到 session 状态文件的行为，具体文件由架构师定）。
- **P0-10 i18n 四语言（必须）**：zh-CN / en / ja / ko 四种语言全部补全新 tab 名称与所有面板文案。

### P1 —— 增强

- **P1-1 长期归档文件（应具备）**：把祈愿历史/聚合持久化到独立的长期归档文件（对标 `record_log.json` 的定位），**不随会话重置清空**，供跨会话累计。
- **P1-2 滚动 1 小时速率（应具备）**：提供 rolling 1h 的「祈愿次数/物品数 per-hour」，用于观察近期节奏（对标掉落 `*RecentPerHour`）。
- **P1-3 与游戏自带计数器交叉校验（应具备）**：展示应用统计的「产出物品总数」与游戏内 `Satistics_TotalOfferingCount`（`祈愿获得的物品数`）的对照，偏差时给出提示，便于用户自证数据可靠。
- **P1-4 RecordLog 祈愿筛选联动（应具备）**：现有 RecordLog 的祈愿筛选 chip（`WISH_RE` / `wish`）继续保留；从祈愿 tab 可一键跳到 RecordLog 并预置祈愿筛选。
- **P1-5 品质分布可视化（应具备）**：用项目现有**自绘 SVG**（禁引入 recharts / chart.js）绘制品质分布图（如横向条或环形），颜色沿用品质色体系。

### P2 —— 可选

- **P2-1 祈愿成本估算（可选）**：若能稳定获得纪念币消耗量，则展示「每次祈愿平均物品数 / 单位纪念币产出」。
- **P2-2 祈愿历史导出（可选）**：把祈愿记录导出为 JSON / CSV。
- **P2-3 时间维度趋势（可选）**：按小时 / 按天的产出趋势折线（自绘 SVG）。
- **P2-4 品质/单品筛选（可选）**：历史列表按品质或单品筛选。

## 5. 统计指标定义（口径统一，避免歧义）

> 以下定义为本 PRD 的**权威口径**，实现与测试均以此为准。

### 5.1 基础事件

- **祈愿次数（offeringCount）**：一次「祈愿结果」事件计 **1 次**。判定依据为识别到一条 `LogMessage_OfferingResult` 结果行（即游戏触发了祈愿结果日志）。**注意**：一次祈愿可能产出多件物品，因此「次数」按**结果事件**计数，不按物品数计数。
- **产出物品数（itemCount）**：一条结果行内解析出的**物品件数之和**（含该行的 `count`，如 `×3` 计 3）。若一行只解析出名称而无数量，按 1 计。**此口径对齐游戏自带 `Satistics_TotalOfferingCount`（祈愿获得的物品数）。**
- **平均件/次（itemsPerOffering）**：`产出物品数 ÷ 祈愿次数`；祈愿次数为 0 时返回 0（不显示 NaN）。

### 5.2 累计 vs 会话

- **累计（cumulative）**：自记录开始（首次祈愿）以来的全部数据；**会话重置不清空**；持久化于长期归档。
- **会话增量（session）**：自最近一次会话重置（或应用启动 / 恢复）以来的数据；重置会话将其归零，同时基于会话基线重新计算速率。

### 5.3 per-hour 速率分母（关键歧义点）

两条速率共用**同一时间分母**，仅分子不同：

- **祈愿次数 per-hour** = `会话祈愿次数 ÷ 会话小时数`
- **产出物品数 per-hour** = `会话产出物品数 ÷ 会话小时数`

**会话小时数（分母）定义**：
1. 时间锚点 `sessionStart` = `min(会话开始时刻, 第一次祈愿事件时刻)` —— 与掉落 `sessionDropStart` 语义一致：**包含等待第一次祈愿的时间**（避免刚重置后 1 次祈愿 / 5 秒 → 720/h 的失真尖峰）。
2. `会话小时数 = max(60 秒, now − sessionStart) ÷ 3600`。**下限钳制 60 秒**（沿用掉落 `MIN_RATE_WINDOW_SEC`），使刚开局时速率保持保守估计。
3. 会话重置 / 恢复时，`sessionStart` 重置为重置时刻；恢复（restore）时锚定到归档中最早的一次祈愿时刻，使会话窗口覆盖完整历史。

**滚动 1 小时速率（P1）分母**：窗口取最近 1 小时（3600 秒），但当窗口内首次祈愿距今不足 1 小时时，取 `max(300 秒, now − 窗口内最早祈愿时刻)`（沿用掉落 `RECENT_MIN_WINDOW_SEC` 的 5 分钟下限以抑制突发尖峰）。

### 5.4 品质分布（gradeDistribution）

- 每条产出物品的**品质**由该物品名称的富文本颜色标签 `<color=#RRGGBB>` 经 `COLOR_TO_GRADE` 映射得到（COMMON / UNCOMMON / RARE / LEGENDARY / IMMORTAL / ARCANA / CELESTIAL）。
- **无法映射**（无颜色标签，或颜色不属于上述 7 种物品色，如宝箱/通关/英雄提示色）→ 归入 **「未知（unknown）」**，**不得猜测品质**（避免错归）。
- 分布以**产出物品数**为分母（非祈愿次数）：
  - `某品质件数 = 该品质下所有物品的件数之和`
  - `某品质占比 = 该品质件数 ÷ 产出物品总数`
  - 各品质件数之和 **必须等于** 产出物品数（自校验不变量）。

### 5.5 单品产出占比（itemShare）

- 按**物品名**（去富文本标签后的纯名称）聚合：
  - `单品产出数量 = 同名物品的件数之和`
  - `单品产出占比 = 单品产出数量 ÷ 产出物品总数`
- 排序：数量降序；数量相同按名称升序（保证稳定）。
- 同名但颜色不同的极端情况：以名称为聚合键（与掉落 `breakdown` 的展示直觉一致）；若实现中发现需要按「名称+品质色」区分，由架构师在设计中标注为待确认项（见 §6）。

### 5.6 数据完整性不变量（供 QA 校验）

1. `累计产出物品数 == Σ 全部单品产出数量`。
2. `累计产出物品数 == Σ 各品质件数（含未知）`。
3. `会话产出物品数 ≤ 累计产出物品数`，且 `会话祈愿次数 ≤ 累计祈愿次数`。
4. 连续 K 次祈愿（每次均产生结果行）后，`祈愿次数` 增量 == K。
5. 会话重置后，所有 `会话*` 归零、所有 `累计*` 不变。

## 6. 待确认问题

> 以下为需架构师或用户澄清的点；不阻塞 P0 主体，架构师可在设计中给出默认选择并标注。

1. **同名不同品质的聚合键**：单品 breakdown 以「名称」聚合（§5.5 默认），还是以「名称 + 品质色」聚合？前者更贴近掉落直觉，后者在极端情况下更精确。**建议默认：按名称聚合**，若实际数据出现同名异色再拆分。
2. **祈愿次数的事件判定边界**：是否需要针对「一次祈愿触发多条结果行」的情况做去重/合并？当前按「每条结果行 = 1 次」计。若游戏实为「一次祈愿 = 一条汇总行」则无歧义；架构师可结合实际日志样本确认是否需要类似掉落的 burst 合并（`LiveChestDropAggregator`）机制。
3. **计量单位是否含非物品产出**：若祈愿结果行偶尔包含金币/经验（`kind: gold/xp`），它们是否计入「产出物品数」？**建议 P0：不计入物品数**，品质分布与单品榜也不含；是否单列由架构师定。
4. **长期归档文件命名与位置**：P1 归档文件的具体文件名/路径（如 `wish_record.json`）与是否复用现有 `record_log.json` 的祈愿行而非另建文件 —— 由架构师定。**产品侧要求：长期累计不随会话重置清空。**
5. **`Satistics_TotalOfferingCount` 的读取稳定性（仅 P1-3）**：游戏自带计数器是否已由现有内存读取覆盖？若未覆盖且读取成本高，P1-3 可降级为「仅应用侧统计」。
6. **业务文档同步**：按项目规范，落地后需更新 `docs/BUSINESS-FLOWS.md` 索引及 `docs/business-flows/` 对应子文件（建议新增或并入 `09-chest-and-autoclassify.md` 同类聚合器章节 + `11-record-log.md`）。具体归属由架构师确定。

## 7. 边界与约束（供架构师参考，非需求）
